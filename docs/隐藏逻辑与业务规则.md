# 隐藏逻辑与业务规则

> 这些是散落在代码里、只有维护者清楚的业务约定。**不理解这些就改代码，大概率会分错线、发错报告。** 主文档见根目录 `CLAUDE.md`。

---

## 1. 路线号的格式约定（最基础，先看这个）

正常路线号格式：`330xx-a-b`
- `330xx` = 大区号（如 33011 Kanata North）
- `a` = 拆分份数（这条大区今天拆成几条线）
- `b` = 第几条子线

例：`33011-2-1` = 33011 大区、拆 2 份、第 1 条。

**中介回复时通常省略中间的 `a`**，只说 `33011-1`、`22-1`（甚至省略 33 前缀）。解析时靠 `services/feedbackParser.ts` 的 `resolveRoute()` 做模糊匹配：大区号后缀匹配 + 末位子线号匹配。

**中介剪线（拆一刀）**产生的行：在原路线号后加 `.1`，即 `330xx-a-b.1`。
再把这一刀分给第二个司机：`330xx-a-b.1.1` 或用 `.2`（`b.2`）。
> ⚠️ 当前本地解析器 `splitSegSuffix()` 只剥**一层** `.n` 后缀。`b.1.1` 这种两级后缀会被当成基线 `b.1` 处理而找不到 → 静默丢弃。这是已知限制，见 `已知问题与技术债.md`。

## 2. Auto-Assign（自动派默认司机）—— 核心隐藏逻辑

**在哪**：`App.tsx` 的 `handleAutoAssign()`，靠 `types.ts` 的 `PLACEHOLDER_MAPPING` 常量。

**原理**：导入取货表后，每条子线的"司机位"先填的是占位符（就是子线号本身，如 `33011-2-1`）。点 Auto-Assign 时，用 `PLACEHOLDER_MAPPING[子线号]` 查出**这条线固定由哪个司机号跑**，替换进去，并带出司机名、团队、时段、区域名。

```
PLACEHOLDER_MAPPING = {
  '33011-2-1': '19492',   // 33011 拆2份时第1条 → 司机 19492 (Fath)
  '33011-2-2': '4574',
  '33014-4-4': '27862',
  '33030-4-4': '27852',   // → Parfait 中介
  ...
}
```

**关键点**：
- 同一大区**按当天拆几份，映射不同**。33011 拆 2 份用 `33011-2-*` 那组；拆 4 份用 `33011-4-*` 那组。取货表里的拆分份数决定用哪一组。
- 映射的目标可以是公司司机，也可以是中介的某个号（如 `33030-4-4 → 27852` 是 Parfait）。
- off 的司机：Auto-Assign 时若该司机在 off 名单里，仍会填上但标记 `isDriverOff`，行变红并出现 Reassign 按钮。**所以务必先在 Availability 面板勾 off，再点 Auto-Assign。**
- 占位符没有映射（新线/临时线）时，只更新区域名和时段，司机位保持占位符不动。

**要改某条线的默认司机**：改 `PLACEHOLDER_MAPPING` 对应键的值。步骤见 `维护操作指南.md`。

## 3. 相关业务常量（都在 `types.ts`）

| 常量 | 作用 | 举例 |
|------|------|------|
| `PLACEHOLDER_MAPPING` | 子线号 → 默认司机号（Auto-Assign 用） | `'33011-2-1': '19492'` |
| `INITIAL_DRIVER_REGISTRY` | 内置司机名册（号→名字+团队+容量） | `'19492': {name:'Fath', group:'Company'}` |
| `ZONE_NAMES` | 路线号 → 中文/英文区域名 | `'33050-1': 'Brookville'` |
| `SCAN_ID_MAP` | 大区号 → 扫描号（报告按扫描号分组） | `'33011': '8257'` |
| `DEFAULT_TIME_SLOTS` | 大区号 → 默认取货时段 | `'33022': '08:00 AM'` |
| `DEFAULT_SPLIT_COUNTS` | 大区号 → 常规拆分份数 | `'33014': 4` |
| `DRIVER_MAX_CAPACITIES` | 司机号 → 最大容量（拆线超限提醒用） | `'6725': 150` |
| `BROKER_MIN_CUT` | 剪给中介的最小件数门槛 | `120` |
| `AGENCIES` | 五个中介团队名 | `['Alain','Alawi','Kaneza','Parfait','Chris']` |
| `REMOVED_DRIVER_IDS` | 已离职、永久清除的司机号 | `['2218','26133','6087']` |

司机名册的团队字段取值：`Company` / `Unassigned` / 五个中介之一。中介司机的名字统一是 `"<团队> Team"`（如 `Kaneza Team`）。

## 4. WhatsApp 报告格式约定

**在哪**：`App.tsx` 的 `AgencyReport` 组件里的 `generateWhatsAppMessage()`。

每个团队一张卡片、一份报告。**公司司机报告和中介报告格式不同**：

**公用结构**：
```
*<团队名大写>* | <日期>[ | <批次号>]      ← 批次号只有中介报告有
<空行>
📍 *<扫描号>*                            ← 按扫描号分组，组内按路线号排序
• <司机号>[ - <司机名>][ @ <时段>] (#<简化路线号>)[ [<区域>]][ [<件数>]]
• ...
📍 *<下一个扫描号>*
...
<空行>
*Sum:* <N> Routes[ / <总件数> items]     ← items 只有中介报告有
<空行>
Tomorrow's routes, thanks
[We are holding <被 hold 的路线号，用中文逗号「，」连接>]   ← 有 hold 才出现
```

**公司 vs 中介的差异**：

| 项 | 公司报告 | 中介报告 |
|----|----------|----------|
| 标题批次号 | ❌ 不显示 | ✅ `date | batchId` |
| 司机名 | ✅ ` - Fath` | ❌ 只有司机号 |
| 件数 | ❌ 不显示 | ✅ ` [147]` |
| Sum 行件数 | ❌ | ✅ ` / 866 items` |

**约定细节**：
- **按扫描号分组**：扫描号 = `SCAN_ID_MAP[大区号] || route.scanId`。同一大区的多条子线归到同一个 `📍 扫描号` 下。
- **简化路线号** `simplifyRouteNum()`：`330xx-a-b` → `330xx-b`（**去掉中间的拆分份数 a**）。中介只关心大区和子线号。
- **只发已分配、未 hold 的线**（`!isHold`）。Hold 的线单独列在末尾 "We are holding …"。
- 团队名从 `group.name` 去掉 `"Team "` 前缀；公司组名是 `"Company Drivers"`，标题写 `DISPATCH`。

改报告格式 = 改 `generateWhatsAppMessage()`。改分组/排序逻辑要小心，中介靠这个对账。

## 4.5 取货表粘贴导入的解析约定（2026-08 公司系统改版后）

**在哪**：`services/textTableParser.ts` 的 `parsePastedDispatchTable()`。

**怎么认行**：把整段文字按 **行首的 `33xxx`**（后面不跟数字或短横）切成一块块，一块 = 一个大区行。这条规则带来两个重要后果：

1. **换行的规则列不会被误判成新行**——`33012-3-2),353-580(...)` 这种续行不是行首 33xxx。
2. **粘两页没问题**：公司系统 2026-08 改版后表格分页（每页 10 行、共 18 行），把第一页和第二页**依次粘在同一个输入框**里即可一次导入；中间夹的 "Rows per page / 1-10 of 18 / Dispatch Planning / Plan Details - …" 页脚页头统统不是行首 33xxx，被自动跳过。连 `1-10 of 18` 也不会被当成区间段（区间段必须形如 `1-256(19492)`，要有括号）。

> ⚠️ 导入是**整表替换**（`App.tsx handlePasteTableImport` 里 `setRoutes(...)`）。所以绝不能分两次导入——第二次会把第一页覆盖掉。

**各列怎么取**：

| 字段 | 取法 | 注意 |
|------|------|------|
| 大区号 | 行首 `33\d{3}` | |
| 扫单号 | 该块里第一个 `8\d{3}` | |
| **货量 (Shipments)** | **扫单号之前的最后一个独立数字** | 见下方坑 |
| 预派发规则 | 所有 `起-止(标识)` 形式的区间 | |
| 批次号 | 全文里的 `OSUB-\d+` | |

> 🕳 **踩过的坑**：旧版表格「团队 ID」列是一个短横 `-`，所以老代码取"路线号之后第一个数字"当货量正好对。新版这列变成了数字 **`0`**，于是每行货量都被解析成 0（导入提示里的"共 X 件"显示 0）。现已改为取**扫单号前的最后一个数字**，新旧格式都正确。各条子路线自己的件数一直是对的（来自区间段 `end-start+1`），受影响的只有 `batchInfo.totalVolume` 这个汇总数。

**规则列里是占位符还是真司机号**，取决于公司系统里那张表提没提交（`buildRoutesFromRows` 两种都支持）：
- **未提交**：`1-256(33011-2-1)` → 括号里是占位符 → 路线号取占位符本身，司机待 Auto-Assign 填
- **已提交**：`1-256(19492)` → 括号里是真实司机号 → 路线号自动编成 `33011-1`、`33011-2`…，司机直接就位

日常晚上排班导入的是**未提交**状态（占位符），所以要点 Auto-Assign。

> 拆分份数列（Split Count）**解析器完全不用**——实际观察到它和区间段数经常对不上（如 33011 显示 2 却有 3 段），以区间段为准。

## 5. 中介反馈解析（本地规则优先，AI 兜底）

**在哪**：`services/feedbackParser.ts`。

流程：`parseFeedbackTextLocal()`（纯规则，瞬时）先跑；**只有它一条都解析不出**时，才 `await parseBrokerFeedback()`（调 Gemini，需 key）。

本地解析器认识 **5 种中介各自的回复风格**（每个中介写法不同），在 `parseLine()` 里逐个正则匹配：
1. **Christ**：`Driver ID 19749: 33020 - 2 (1 - 150)`（范围 1-150 表示 150 件）
2. **本项目自己的报告格式回传**：`• 15165 @ 06:00 AM (#33018-1) [Orleans E] [147]`
3. **Kaneza**：`22-1: 20059(190) to 12588(100)`（一行多司机）
4. **Parfait**：`28715-33018-2. 135pkges`（司机号在前，然后路线，然后件数）
5. **Alain/通用**：`18944 29-1 #120` / `19994 14-1` / `18944 29-1 120件`

**套用语义**（`applyFeedbackOps()`）：按"部件"更新——每个 segment 精确指向某一部件（基线行 partIdx=0，或 `.n` 刀行），**只改提到的部件，没提到的不动**。总量守恒：套用后该大区总件数保持不变（差额自动补到基线或最后一个显式件数的段）。

**清洗**：WhatsApp 复制常带不可见字符（U+200B ZWSP、U+2060 word joiner 等），`parseLine()` 开头会先 strip 掉。

遇到名册里没有的司机号 → 弹窗问是否**临时添加**到该中介（temp 司机）。这些进 `yow-pending`，可在 Drivers 页批准转正。

## 6. 日期与"排明天的班"

- **dispatchDate 永远是"明天"**（渥太华/多伦多时区）：`getOttawaTomorrowDateString()`，格式 `MM/DD/YYYY`。晚上排的是第二天的班。
- 导入取货表时，发货日期自动填明天，不用手改。
- **每日历史存档 id** 由日期转成 `yow-day-YYYY-MM-DD`（`cloudSync.ts` 的 `archiveIdFromBatchDate()`），可排序。

> `types.ts` 里还有 `getMechanismForDate()`（按周奇偶返回 1/2）和一整套 E-binder 日期解析函数（`normalizeEbinderDate` 等）——这些是**司机请假还靠 E-binder 截图时代的遗留**，现在请假纯手动，基本不再走这条路。改动时可忽略，但暂未删除。

## 7. Hold 建议规则

**在哪**：`services/holdSuggestions.ts`。

偏远线货量低于门槛时，Editor 表格上方自动出现 Hold 建议条（建议今天不派、押到明天一起送）。门槛（"以下"含本数，即 `≤`）：

| 线 | 门槛 |
|----|------|
| Brookville | ≤ 120 |
| Calton Place | ≤ 100 |
| Renfrew | ≤ 100 |
| Perth | ≤ 100 |
| 55-3 + 55-4 合计 | ≤ 150 |

识别方式：路线的 Location 列文字 + 路线号反查 `ZONE_NAMES`（Location 被清空也能靠路线号认出）。已 hold 的行和 0 件行不触发。改门槛 = 改 `holdSuggestions.ts` 里的 `HOLD_RULES` 数组。

## 8. 拆线数量实时提醒

**在哪**：`SplitModal` 组件。

拆线弹窗里实时标红（**只提醒，不拦操作**）：
- 剪给中介的部分 `< BROKER_MIN_CUT`（120）→ Part 2 变红「给中介少于 120 件，中介可能不接单」
- 司机保留部分 `> 该司机的 maxCapacity`（如 Saiki 150）→ Part 1 变红「超过上限」

## 9. 名册合并优先级（容易踩的坑）

司机名册来自多个源，合并时的优先级：
- 代码内置 `INITIAL_DRIVER_REGISTRY` 是基础
- localStorage `yow_dispatch_registry` 覆盖它，但**带 `edited: true` 的条目**（用户在 Drivers 页手动改过的）优先于代码默认值
- `REMOVED_DRIVER_IDS` 和删除墓碑（`yow_dispatch_deleted` / `yow_temp_deleted`）里的号一律清除
- 云端 `yow-roster` 拉下来后合并正式名册；`yow-pending` 合并临时司机（但跳过墓碑里的号）

改内置名册（`types.ts`）后，如果某人浏览器里有 `edited` 的同号旧数据，代码改动对他不生效——这是"改了没变化"类问题的常见原因。
