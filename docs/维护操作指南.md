# 常见维护操作指南

> 分步操作手册。**第 0 节是给调度员/同事看的每晚排班流程**（不用懂代码）；A 节之后是给维护者的改代码操作。业务背景见 `隐藏逻辑与业务规则.md`。

---

## 0. 每晚排班操作流程（调度员用｜2026-08 更新）

> 晚上排的是**第二天**的班。系统里的日期自动就是明天，不用改。

### 第 1 步：导入取货表

⚠️ **公司系统 2026-08 改版了：表格分成两页（每页 10 行，共 18 行）。**

1. 点紫色的 **Paste Dispatch Table**
2. 公司系统第 1 页 → 全选（Select All）→ 复制 → 粘进输入框
3. 翻到第 2 页 → 全选 → 复制 → **接着粘在同一个框的下面**（不要清空，不要分两次导入）
4. 点「导入 →」

**为什么可以直接接着粘**：解析器只把**行首的 33xxx** 当成新的一行，中间夹的 "Rows per page / 1-10 of 18 / Dispatch Planning / Plan Details…" 这些页码表头文字会被自动忽略。

> ❌ **千万别分两次导入**：第二次导入会**整表覆盖**，第一页的 10 个大区会全部消失。
>
> 💡 也可以把右下角 "Rows per page" 调大（能一页显示完 18 行），那就跟以前一样一次复制。

**导入后立刻核对**：提示条会显示「X 个大区 · Y 条子路线 · 共 Z 件」。
- 大区数应该是 **18**（少了就是漏粘了一页）
- 件数 Z 应该和公司系统各行 Shipments 之和对得上（显示 0 说明解析出问题，找维护者）

### 第 2 步：勾选明天请假的司机

在 Availability 面板里勾掉明天 off 的人。**必须在点 Auto-Assign 之前勾**，否则派完还要一个个改。

### 第 3 步：Auto-Assign（自动派默认司机）

点蓝色 **Auto-Assign**，系统按固定映射把每条线派给默认司机。
- off 的司机那行会**变红**并出现 Reassign 按钮 → 点开换人
- 想改某条线的**长期默认司机**，那是改代码，见下面 B 节（或找维护者）

### 第 4 步：拆线给中介

需要把线剪一刀给中介时点该行的拆分按钮：
- 上半部分 = 司机自己留的量，下半 = 剪给中介的量
- 剪给中介**少于 120 件会标红**（中介可能不接单）；司机留的超过他的上限也会标红
- 只是提醒，不拦你操作

### 第 5 步：发 WhatsApp 报告

Reports 页 → 每个团队一张卡片 → 复制或直接点发送到对应群。

### 第 6 步：收中介反馈并套用

中介回复后：点 **Paste Broker Feedback** → 整段粘贴 → 看预览的「改前 → 改后」→ 确认无误点套用。
- 预览里**加粗的司机号 + 彩色团队徽章 = 改后的结果**；灰色划线的是被换掉的原司机
- 中介偷懒把两半都写成同一个路线号（如两行都是 `33018-1`），系统会自动识别成"基线 + 一刀"，不用手改
- 遇到名册里没有的司机号，会问你要不要登记为临时司机

### 第 7 步：回填公司系统 + 保存

1. Allocations 页 → 按顺序复制分配区间串 → 回填公司系统
2. 点 **☁↑** 保存到云端（同事才看得到；同时自动存一份当天历史存档）

### 每晚必记的三件事

| 事项 | 说明 |
|------|------|
| **☁↑ 保存** | 不点就只存在你自己电脑上，同事看不到 |
| **改了司机名册要点 Update（密码 1011）** | Drivers 页的增删改**不会自动上传**，必须手动点蓝色 Update |
| **看到"云端有同事保存的更新"弹窗先点取消** | 先 ☁↓ 看一眼，别直接覆盖同事的成果 |

> 多人同一晚排班容易互相覆盖。约定：**同一时间只有一个人排，排完 ☁↑，下一个人先 ☁↓ 再接着改。**

## 维护者部分（以下需要改代码）

每个改动后都遵循同一个收尾：`npm test` → `npm run build` → commit → push 到部署分支（自动上线）。

通用收尾流程：
```bash
npm test          # 必须全绿（改 services/ 和 types.ts 时尤其重要）
npm run build     # 确认能构建
git add -A && git commit -m "说明"
git push          # push 到 main 或当前部署分支 → GitHub Actions 自动部署，1-2 分钟上线
```
> 当前部署分支：`main` 和 `claude/scheduling-system-improvements-pf3cni`（见 `.github/workflows/deploy.yml`）。没有预发环境，push 即上线。

## A. 加 / 改 / 删一个司机

**优先用界面，不用改代码**：Drivers 页 → 增删改 → 点 **Update to Supabase（密码 1011）** → 全组同步。这样不用发版。

**要改代码内置默认名册**（`types.ts` 的 `buildInitialRegistry()`）：
```ts
// 加：在对应团队区块加一行
'12345': { name: 'NewGuy', group: 'Company' },   // 或 group: 'Kaneza' 等
// 删（离职）：从名册删掉那行，并加进 REMOVED_DRIVER_IDS
export const REMOVED_DRIVER_IDS = ['2218', '26133', '6087', '12345'];
```
> 注意名册合并优先级（见隐藏逻辑文档第 9 节）：如果同事浏览器有 `edited` 的同号旧数据，代码改动对他不生效，需要他在 Drivers 页手动改或清缓存。离职建议**同时**在 Drivers 页删一次 + 改代码 `REMOVED_DRIVER_IDS`，双保险。

司机最大容量（拆线提醒用）：改 `types.ts` 的 `DRIVER_MAX_CAPACITIES`。

## B. 改路线配置

路线相关常量全在 `types.ts`。按需要改：

| 想改什么 | 改哪个常量 | 例 |
|----------|-----------|-----|
| 某条子线的**默认司机**（Auto-Assign） | `PLACEHOLDER_MAPPING` | `'33030-4-4': '27852'` |
| 路线的**区域名** | `ZONE_NAMES` | `'33050-1': 'Brookville'` |
| 大区的**扫描号** | `SCAN_ID_MAP` | `'33011': '8257'` |
| 大区的**默认取货时段** | `DEFAULT_TIME_SLOTS` | `'33022': '08:00 AM'` |
| 大区的**常规拆分份数** | `DEFAULT_SPLIT_COUNTS` | `'33014': 4` |

**改默认司机的完整例子**（把 33030-4-4 从某号改成 27852）：
1. `types.ts` → `PLACEHOLDER_MAPPING['33030-4-4'] = '27852'`
2. 确认 27852 在名册里（`buildInitialRegistry` 有这个号 + 正确团队），没有就一起加
3. 如果这个号属于某中介，`ZONE_NAMES` 里该线名字也确认一下
4. `npm test && npm run build` → commit → push

> Hold 门槛改 `services/holdSuggestions.ts` 的 `HOLD_RULES`；中介最小剪线量改 `types.ts` 的 `BROKER_MIN_CUT`。

## C. 给司机加一个新字段（数据模型改动）

例：给司机加"电话号"字段。涉及类型 + 名册 + 可能的 UI，步骤：

1. **改类型** `types.ts`：
   ```ts
   export interface DriverRegistryEntry {
     name: string;
     group: string;
     maxCapacity?: number;
     phone?: string;        // ← 新增，用可选字段保证向后兼容
     edited?: boolean;
     temp?: boolean;
   }
   ```
2. **需要内置默认值**就在 `buildInitialRegistry()` 对应司机加 `phone: '...'`。
3. **要能在界面编辑**：在 `App.tsx` 的 `DriversView` 里加输入框，并让 `handleUpsertDriver` 带上新字段。
4. **要云同步**：字段在 `DriverRegistryEntry` 上，`yow-roster` 存的就是整个 registry，**自动跟着同步**，`cloudSync.ts` 不用改。
5. **加个单测**（`tests/cloudSync.test.ts` 的 roster round-trip 里断言新字段）。
6. 收尾流程。

> 原则：数据模型加字段**一律用可选字段**（`?`），否则旧的云端数据/localStorage 反序列化后缺字段会出问题。

## D. Gemini API key 轮换

**背景**：key 不在代码里，每个用户存自己浏览器（localStorage `gemini_api_key`）。所以"轮换"通常是针对个人的操作，不用发版。

**个人换 key**：页面右上角钥匙图标 → 粘贴新 key → 保存。旧 key 到 Google AI Studio / Google Cloud Console 删除即可。

**如果 key 泄露了**（进了代码/提交历史/聊天/公开 bundle）：
1. **立刻**去 Google AI Studio 或 Google Cloud Console **吊销**那个 key。
2. 生成新 key，只在页面里填（不要写进任何文件）。
3. 如果泄露的 key 进了 git 历史，光删文件不够——历史里还在。要么接受吊销后作废（推荐，简单），要么用 `git filter-repo` 清历史（麻烦，且 GitHub push protection 可能已经拦了提交）。
4. 检查 `vite.config.ts`：它会把构建时的 `GEMINI_API_KEY` 环境变量烤进 `process.env.API_KEY`。**确保 CI/本地构建环境没设这个变量成真实 key**，否则会被打进公开 bundle。正常情况这个变量应为空。

> ⚠️ 铁律：真实 key 绝不进代码、`.env`（会被构建烤进 bundle）、commit、聊天记录。本项目历史上因此被 Google 作废过一次 key。

## E. 换 Supabase 项目 / 改连接

改 `services/cloudSync.ts` 顶部两个常量：
```ts
const SUPABASE_URL = 'https://xxxx.supabase.co';
const SUPABASE_ANON_KEY = 'eyJ...';   // 匿名 publishable key，公开无妨
```
新项目要先建表：
```sql
create table dispatch_snapshots (
  id text primary key,
  data jsonb,
  updated_at timestamptz
);
alter table dispatch_snapshots enable row level security;
-- 开放匿名读写（安全性靠团队口令加密）
create policy "anon all" on dispatch_snapshots for all
  to anon using (true) with check (true);
```
> 临时/单机覆盖不发版：浏览器 localStorage 存 `supabase_config` = `{"url":"...","key":"..."}`。

## F. 改团队加密口令

- 口令存在每个用户浏览器 localStorage `team_passcode`，通过右上角设置填。
- **全组必须用同一个口令**，否则互相解不开云端数据。
- 换口令时：先让保存者用**新口令**重新 ☁↑ 保存一次（用新口令加密），其他人再改成新口令拉取。中途会有人短暂解不开——最好约个时间统一切。
- 想彻底不加密：所有人清空 `team_passcode`，然后重新保存一遍（存明文）。
